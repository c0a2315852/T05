# T05 農業集荷ルート最適化

集荷地点の担当車両(割当)を入れ替えて、総移動時間を短くする局所探索のプログラムです。
候補の探索を**荷量索引**で絞り込む版と、全候補を調べる素朴な版(比較用)を、同じ入出力で切り替えて比べられます。
標準ライブラリだけで動きます(Python 3.9以上。動作確認は3.12)。

## フォルダ構成
```
t05route/
  model.py    問題の定義、経路の組み立て(最近傍→2-opt→納入先の挿入)、納入量の配分、状態の評価
  search.py   割当の局所探索(移動・交換)と荷量索引
  replan.py   事前予測と実荷量が違うときの再計画、指示変更の数え方
  data.py     CSVの読み書き
  gen.py      疑似データの生成(乱数の種を固定)
  cli.py      コマンドライン
data/sample9/ 机上実験の9拠点(厳密解との比較用)
tests/        テスト
```

## 使い方(リポジトリの直下で実行)
```
# 1. 荷量索引あり/なしを比べる(結果の一致、候補数、計算時間)
python -m t05route compare --data data/sample9
python -m t05route compare --data data/sample9 --capacity-mode segment

# 2. 1つの方式で解く
python -m t05route solve --data data/sample9 --algo index      # index か baseline

# 3. 疑似データを作る(拠点数・車両数・乱数の種・予測誤差・充填率)
python -m t05route generate --out data/generated/g20 --sites 20 --vehicles 3 --seed 1 --noise 0.2 --fill 0.9
python -m t05route compare --data data/generated/g20

# 4. 事前予測で計画 → 実荷量で再計画(指示がいくつ変わるか)
python -m t05route replan --data data/generated/g20

# テスト
python -m unittest discover -s tests -v
```

## CSV仕様(data/ の下のフォルダに5ファイル)
| ファイル | 列 | 備考 |
| --- | --- | --- |
| sites.csv | site_id, forecast_kg, actual_kg | 事前予測の荷量と実荷量(整数kg) |
| vehicles.csv | vehicle_id, capacity_kg, fixed_first_site | 最初に訪問する拠点を固定するなら拠点ID、なければ空 |
| destinations.csv | dest_id, limit_kg | 納入先ごとの受入上限 |
| travel_time.csv | 先頭行・先頭列が地点ID(車庫は `D`、納入先は `T` `M` など) | 分。全地点の組が必要 |
| initial_assignment.csv | vehicle_id, site_id | 初期の割当。全拠点をちょうど1回ずつ |

`--load actual`(既定)は実荷量、`--load forecast` は事前予測で計画します。

## 仕様と仮定(チームで変えてよい。変えたら README を更新)
1. **評価の順序**(擬似コードどおり): ①制約違反数 ②総移動時間 ③変更地点数。違反数は「容量を超えた車両の数 + 受入上限を超えた納入先の数」。
2. **変更候補**: 1地点の担当車両の変更(R)と、2地点の交換(S)。最良の候補を選び、改善がなければ終了。
3. **経路**: 集荷順は最近傍法 → 2-opt。そのあと納入先の訪問を挿入する。各納入先は車両あたり最大1回、最後は必ず納入先。集荷の途中で納品し、その後にまた集荷してもよい。
4. **容量の考え方**(`--capacity-mode`):
   - `total`(既定・擬似コードどおり): 車両の**総集荷量**が容量以内。
   - `segment`: 納入先で降ろす前提で、**区間ごとの積載量**が容量以内。机上実験の最短経路(255分)はこちら。
5. **荷物は混載でき、納入先で量を分けて降ろせる**。降ろす量は、受入上限の残りを先に使う貪欲法で決める(最適とは限らない)。
6. 積み降ろし時間は0分。所要時間は表の値のみ。
7. 受入上限は「上限」。上限の合計が総荷量より小さいと、必ず超過になる。
8. 拠点6の所要時間は、資料どおり「2・4・5の平均(自分自身を含む)」(`data/sample9/travel_time.csv`)。

## 荷量索引
車両ごとに、担当拠点を荷量の小さい順に並べた一覧です。残りの積載量を `slack` とすると、
- 移動(s を a → b): 荷量 w_s ≤ slack_b の拠点だけ
- 交換(s∈a, t∈b): 荷量 w_t が [w_s − slack_b, w_s + slack_a] に入る組だけ

を二分探索で取り出し、そのほかは評価しません。採用した変更のある車両の分だけ索引を更新します。
**絞り込みを使うのは「現状に違反がない」「`total` モード」のときだけ**です(違反のある候補は必ず現状より悪くなるため、結果は索引なしと一致します。テストで確認しています)。

## 動かしてわかったこと(この実装、乱数の種1つ、20拠点・3台の例)
| 充填率(総荷量/総容量) | 評価した候補(索引なし → あり) | 計算時間 |
| --- | --- | --- |
| 0.8 | 1,003 → 971(約3%減) | ほぼ同じ |
| 0.9 | 2,052 → 1,109(約46%減) | 約45%減 |
| 0.97 | 1,551 → 424(約73%減) | 約68%減 |

- **容量に余裕があると、索引はほとんど効きません**(違反する候補が少ないため)。効果は、積載がぎりぎりの状況で大きくなります。
- 1つの種での例です。複数の種・拠点数で測り直してから、結論を書いてください。
- 時間の大半は、候補ごとの経路の再計算(2-opt)です。索引は評価する候補を減らしますが、1候補あたりの時間は変えません。

## 机上実験との対応
`data/sample9` の `segment` モードでは、初期割当(以前の案、303.33分)から255分(A 165分・B 90分)に到達します。これは厳密探索で確認した最短と同じです。`total` モードでは、この経路は容量超過(Aの総集荷量2,433kg)になるため、303.33分のままです。

## 既知の制限・今後の課題
- 経路は近似(最近傍+2-opt)です。厳密解より悪くなることがあります。
- 納入先の訪問パターンの選択は山登り法で、全組み合わせは調べていません。
- 索引は `total` モード限定です(`segment` では絞り込みなし)。
- 再計画の指標は簡易版です(担当が変わった拠点数、次の行き先が変わった地点数)。
- 計算時間はPythonでの相対比較用です。
- 拠点50で約47秒かかります(経路の再計算が重い)。100拠点以上は、経路のキャッシュや2-optの高速化が必要です。
